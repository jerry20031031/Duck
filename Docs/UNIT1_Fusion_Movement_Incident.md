# UNIT1：Fusion 角色與敵人不移動的除錯紀錄

日期：2026-09-29  
範圍：BigHall 進入 UNIT1 後的本機玩家與灰影鴨子敵人。

## 現象

- 玩家進入 UNIT1 後，WASD 沒有效果；跳躍也異常。
- 三隻灰影鴨子同樣不巡邏，像停在原地或飄著。
- 初期曾出現出生高度、鏡頭、角色外觀延續等其他問題；但「玩家和敵人都無法走路」是另一個共同的移動問題。

## 關鍵證據

Console 顯示：

```text
[UNIT1-DIAG Player] ... stateAuthority=True ... moverEnabled=True ...
[UNIT1-DIAG Enemy] ... stateAuthority=True | kinematic=False | gravity=True
[UNIT1-DIAG Enemy] patrol/chase movement started ... velocity=(-0.39, 0.00, 1.13)
```

這三行很重要：

1. 玩家不是因為沒有 StateAuthority 而不能控制。
2. 敵人不是因為 AI 沒有執行；它已經算出巡邏目標與速度。
3. 速度已被寫入，卻沒有看見座標前進。因此下一步不能再猜輸入、敵人目標或 Collider，而要檢查「速度到座標」這一段。

## 原本的錯誤做法

一開始讓 `DuckMover.FixedUpdate()` 寫 `Rigidbody.linearVelocity`，同時角色上有 Fusion `NetworkTransform`。

後來雖然把移動改進 `FixedUpdateNetwork()`，仍然只寫 `linearVelocity`。這只修正了 **誰在什麼 tick 寫速度**，沒有修正 **誰負責產生並同步最終座標**。

在這個專案的 Fusion 場景流程中，Unity Rigidbody 的速度積分與 Fusion `NetworkTransform` 的狀態擷取／套用是不同的時序。結果是速度有值，但角色最後沒有可靠地前進；玩家和敵人都使用同一模式，所以一起失效。

> 不要把「Console 顯示 velocity 非零」當成「角色一定會移動」。一定要再驗證 position 是否真的改變。

## 最終架構：Fusion tick 的 kinematic motor

目前改為下列單一路徑：

```text
玩家輸入／敵人 AI
        ↓
FixedUpdateNetwork（僅 StateAuthority）
        ↓
DuckKinematicMotor.Move
  ├─ Rigidbody.SweepTest：先檢查牆、物件、其他 Collider
  └─ Rigidbody.position：直接提交安全的位移
        ↓
NetworkTransform 同步這個最終 Transform
```

- Rigidbody 保持 `isKinematic = true`、`useGravity = false`；它是碰撞殼，不再交給 Unity 自動積分速度。
- `DuckKinematicMotor` 先用 `SweepTest` 找出阻擋物，再將位置移到碰撞前的安全距離，因此外牆與地圖物件仍有碰撞效果。
- 玩家在 `DuckMover` 內自己管理垂直速度、重力、跳躍與地面偵測；地面偵測不限定圖層，任何有效 Collider 都可成為落腳處。
- 敵人使用同一個 motor，所以玩家與敵人的基礎移動行為一致。

## 下次遇到「角色不動」的檢查順序

1. **先找共同點。** 如果玩家與敵人同時不動，優先查共用移動層、物理設定或場景生命週期，不要先只修玩家輸入。
2. **分開驗證四件事：**
   - `FixedUpdateNetwork()` 是否在跑？
   - `HasStateAuthority` 是否為 `true`？
   - 輸入／AI 是否產生目標位移？
   - `transform.position` 是否真的在下一個 tick 改變？
3. **Collider 與地板是下一層。** 只有在座標真的改變但被彈回、卡住或下墜時，才查牆、地板、出生點與 Capsule 尺寸。
4. **不要讓兩套系統都寫位置。** Unity `FixedUpdate`、Fusion `FixedUpdateNetwork`、NetworkTransform 校正、場景轉移定位，必須明確指定唯一擁有者。
5. **重新 Play 驗證。** 改變 NetworkObject、Rigidbody 或場景轉移後，先 Stop 再 Play，避免舊的網路物件狀態干擾結果。

## 這次最值得記住的一句話

**在網路遊戲裡，速度值正確不等於角色位置會正確；要追到最後真正寫入並同步 Transform 的那一行。**

## 2026-10-05：有路徑，但 CPU 停在第一個轉彎點

這次是另一個問題，不能沿用上面速度／同步時序的推論。用暫時性的 Editor 探針，從 BigHall 的獨立 Fusion Shared 房間進入 UNIT1，每秒讀取真正的 `transform.position`、`Rigidbody.position`、路徑索引與 motor 呼叫；每隻記錄八次。

### 修正前的實際證據

- 三隻 CPU 都有 StateAuthority，Fusion tick 與 DeltaTime 正常。座標連續數秒不變，路徑維持第 0 點。
- 它們距離當前路徑點約 0.696、0.735、0.752m。`MoveTowards` 把拾杖停止距離 0.78m 套用到中途路徑點，因此提早 return；但 scanner 要到 0.42m 內才切下一點。兩者形成永遠無法前進的死區。
- 灰影的移動函式也有同一錯誤，尤其 2m 以上的跟隨／攻晶／防守範圍會更早停在中途。
- 灰影 2 的巡邏目標找不到路，卻一直重試同一個目標，八次座標均為 `(68.8, -0.334, 26)`。另外兩隻灰影在這個重現場景已有移動，不應描述為全部 motor 都失效。

### 修正

1. CPU 與灰影只對**最終目標**檢查拾杖／攻擊／跟隨停止距離；中途路徑點交由 scanner 的近距離門檻切換，不再套用戰術距離。
2. 每 tick 位移不超過到當前路徑點的剩餘距離，避免低 tick rate 時越過轉彎點。灰影用 `body.position` 計算方向，與 motor 使用的座標一致。
3. 繞路恢復點使用自己的近距離門檻，不使用攻擊距離。
4. 灰影巡邏無路可走時短暫等待並重新挑點，不穿牆，也不永遠鎖死在失敗的目標。

## 2026-10-05：CPU 會走，但拿不到手杖

上一項測試只驗證移動，沒有驗證拾杖，不能據此判定完整 AI 流程正常。

CPU 的拾杖接近距離是水平 0.78m，但 `Unit1WandPickup` 原本使用角色根節點到手杖根節點的 3D 球形距離，半徑 1.5m。CPU 落地後根節點 Y 約 -0.5992，場景手杖 Y 為 1.1；光是高度差 1.6992m 就已超過上限，即使水平距離為零也永遠拾取失敗。

共用拾取判定改成水平半徑 1.5m 與獨立高度差上限 2.2m；CPU、灰影的直接拾取與玩家 RPC、玩家本機可拾取查詢都使用 `CanBePickedUpBy`。保留可用性與 StateAuthority 檢查，沒有取消距離或高度限制。

從 BigHall 的獨立 Fusion Shared 測試房間進入原 UNIT1 地圖，暫時的唯讀 Editor 探針確認：

- CPU 3 拿到「虛空重擊杖 2」。
- CPU 1 拿到「水晶守護杖 1」。
- 三隻的 `HasWand` 均為 true、`HolderObjectId` 均對應該 CPU，手杖 `visualRoot.parent` 均為該角色的右手骨頭。
- 水平 0.78m／高度差 1.6992m 可拾取；水平 1.51m 拒絕；高度差 3m 拒絕；高度差反方向 1.6992m 也可拾取。

這是本機 StateAuthority 端的拾杖與持杖呈現驗證，不是遠端多客戶端同步測試。

## 2026-10-05：灰影比照 CPU，解除出生區域限制

灰影原本仍有獨立的局部活動設定：只搜尋 18m 內的手杖、7m 內的敵人，沒有目標時只在出生點 2.2m 半徑巡邏；巡邏／追趕速度也只有 1.2／2m/s。共用路徑規劃器並不會自動解除這些目標選擇限制。

### 正式行為調整

- `EnemyDuckAI.useWholeMapObjectives` 與灰影 prefab 預設開啟：全圖搜尋可用手杖與合法敵人，保留陣營、淘汰、是否持杖等戰鬥規則；18m／7m／出生點半徑只供關閉全圖模式時使用。
- 未持杖時優先尋杖。遠處手杖不再因評分低於閒逛而被忽略；不藉由未持杖的攻擊計畫免費施法。
- 巡邏從**目前位置**選下一段探索路線，候選距離 12～28m，再檢查落腳地面與 A* 路線是否存在；不是把出生點的固定小圈單純放大。
- 巡邏速度 2.2m/s、追趕／尋杖速度 3.45m/s，與 CPU 預設一致。繼續使用 `Unit1RouteScanner` 與 `DuckKinematicMotor`，不直接穿過地圖碰撞體。
- 中途路徑點沿用近距離切點；最終目標才使用戰術停止距離。真正受阻時固定一側恢復、必要時換側；符合 CPU 低障礙條件才嘗試跳躍，並加入重力與落地偵測。
- 無法到達的目標最多暫存 8 個、5 秒後可重試。原本只記住一個失敗點，會讓兩個失敗目標互相覆蓋，形成原地換目標循環；換杖或判定無路時清除舊路線，避免沿用上一個目標的重規劃等待。
- 實際拾取使用共用 `CanBePickedUpBy` 的有效水平／高度範圍，不強迫角色走進手杖的中心格；接近路線仍使用 0.78m 目標範圍。保留 StateAuthority、可用性與持有者檢查。

### 分階段 Play 驗證

第一輪保留正常對戰，以唯讀探針觀察原 UNIT1 地圖與出生點。三隻灰影實際離開出生點約 33～51m，灰影 2 拿到快攻杖、灰影 3 拿到重擊杖，兩支的持有者與右手模型都正確。對戰結束後角色停止是正常結算流程，不能把結算後的靜止當成移動失效。

第二輪僅在 Play 期間暫停 CPU 行動、抑制灰影施法，排除快速結算的干擾；不搬動灰影、不強制拾杖、不儲存場景。這輪暴露灰影 1 在兩個不可達手杖間反覆換目標的問題，才補上多目標失敗記憶與共用有效拾取範圍的修正。

修正後第三輪沿用相同隔離方式，三隻都由正式 AI 與拾取函式自行拿杖：灰影 1 拿到「虛空重擊杖 2」、灰影 2 拿到「星光快攻杖 2」、灰影 3 拿到「水晶守護杖 2」。三隻都確認 `HasWand=true`、手杖持有者對應該角色、模型掛在右手；追敵過程的實際出生點距離曾分別達約 52、33、76m。可走的直線段每 2 秒位移約 6.9m；探索選點測試也找到約 13～22m 的有路線目標。

追敵的不可達記憶同時記錄施法站位與對應敵人，不只記錄偏移後的座標；側向恢復仍無進展時限制重試次數，再換目標。拾取後仍短暫保留尋杖計畫時，也禁止重複認領第二支手杖。

臨時 Editor 探針與 meta 已移除；攻擊抑制只存在該探針，不是正式 AI 或場景設定。這次未移動出生點、重建地圖或儲存測試場景。以上是本機 Fusion Shared StateAuthority 端的移動／拾杖驗證；低障礙跳躍、全地圖每個角落及遠端多人同步仍不屬於已完整驗證的範圍。

最終正式腳本與移除探針後的 Editor assembly 均由 Unity 成功編譯（最後一次 Tundra build success，1.28 秒）。重編譯期間另曾出現 Fusion Editor `EditorRecompileHook.ShutdownRunners` 的集合枚舉例外，來源是 Play 期間重編譯的 Runner 關閉流程，不是灰影的 tick；之後重啟的 UNIT1 已完成陣營與開局同步。沒有修改 Fusion 套件來處理這個獨立 Editor 問題。

## 2026-10-06：CPU 間歇停住，CPU／灰影共用導航修正

### 找到的原因

上一輪每秒採樣、暫時抑制攻擊而不強迫目標／位置的 Shared 實測中，六隻一開始都有實際位移。兩隻未持杖 CPU 卻在守護杖／重擊杖之間頻繁換目標：每 0.4 秒的 `RefreshUnarmedPlan` 直接重選手杖，繞過原本的切換門檻；路徑目的地也曾落後於當前手杖。另有已持杖 CPU 與灰影在有效攻擊距離內停止，這是正常行為，不是同一個移動故障。

程式檢查另外找到：CPU 恢復用的 Sweep 與正常 motor 對其他鴨子、地面的過濾不同；恢復失敗沒有更換目標；掃描器在有 Static 地板時會漏掉未勾 Static 的固定道具；A* 只確認格子中心，沒有確認兩個中心之間是否容得下真實碰撞體。

先前臨時探針的 `static=0 nonStatic=0` **不能當作場景沒有障礙物的證據**：它只查 `Generated Map`，而該場景沒有這個根物件。正式掃描器當時已使用場景 Collider 備援。

### 正式修正

- CPU 尋杖固定仍有效的目標，小幅評分／距離變化不再每輪換杖；失效或明顯更好的目標才切換，並同步清除舊路線。拾取使用正式共用的水平／高度判定。
- CPU 與灰影共用 `Unit1NavigationMemory`：最多 8 個失敗目標，5 秒後可重試；選目標時略過尚未到期的失敗點，而不是加分後仍選回同一個目標。CPU 補上恢復失敗的退出流程與重試上限。
- motor 與 CPU 恢復／兩者跳躍檢查共用 `TryGetBlockingHit`。逐個過濾水平地面碰撞，再選最近的真正障礙；AI 的正常位移與恢復都忽略動態鴨子／網路物件，固定牆體仍阻擋。玩家仍保留動態碰撞。
- 掃描納入目前導航場景內所有固定、非網路、非 Rigidbody 的有效 Collider，不依 Static 勾選決定是否算牆。依真正角色 Collider 校準導航膠囊與地面高度。
- A* 相鄰格連線及最終接近路段增加連續膠囊掃掠；連線結果快取。真實位置先安全接到格子中心，中途切點縮到 0.18m 並確認下一段可通過，避免轉角切牆。
- 更換目標立即重規劃，不沿用上一個目的地的等待時間。被占住的目標中心允許在**實際戰術距離內**的可走格結束，不能停在距離外的「最近格」；最後一點也不能提早消耗掉。
- CPU 在 Shared 房主端對尚未取得的 StateAuthority 每秒重試一次；非房主仍不寫入 AI 位移。
